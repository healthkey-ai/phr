### TODO-001: Add NFR-LLM Section to PRD

**What:** Add a new NFR section (NFR-LLM-001 through NFR-LLM-008) to the PRD covering AI/LLM infrastructure requirements.

**Why:** The PRD describes three features that implicitly require LLM infrastructure — document parsing (PAT-012), plain-language summaries (PAT-042), and PHResolution plain-language explanations (PAT-031) — but never specifies model selection, BAA requirements, PHI handling, hallucination mitigation, or fallback behavior. Engineering cannot select an LLM vendor or design the extraction pipeline without these requirements. Sending PHI to a non-BAA LLM provider is an immediate HIPAA violation.

**Required requirements:**
- NFR-LLM-001: LLM vendor must sign a HIPAA Business Associate Agreement (BAA) before any PHI is processed. BAA status must be verified programmatically before each API call category (no silent misconfiguration).
- NFR-LLM-002: Model selection criteria — accuracy benchmarks for clinical document extraction, cost model ($/record), and latency SLA.
- NFR-LLM-003: Sandboxed extraction — LLM document parsing runs with a fixed system prompt that cannot be overridden by document content (prompt injection defense). All extracted fields validated against expected schema before persisting.
- NFR-LLM-004: Hallucination mitigation — extracted structured fields (diagnoses, dosages, dates) require confidence scoring. Fields below threshold are flagged for patient review rather than auto-populated.
- NFR-LLM-005: Fallback behavior — if LLM extraction fails or returns low confidence, document is stored as unstructured attachment with patient notification.
- NFR-LLM-006: Plain-language summary accuracy — summaries must be validated against a clinical accuracy standard (reading level: ≤8th grade; no clinical terms introduced that weren't in the source data).
- NFR-LLM-007: Cost model — per-patient LLM cost must be estimated and capped. Unbounded LLM calls on a large patient base = unbounded cost.
- NFR-LLM-008: Audit trail — all LLM calls logged with input hash (not raw PHI), model version, and output hash for reproducibility and compliance.

**Pros:** Unblocks LLM vendor selection, ETL architecture, and compliance design. Prevents HIPAA violation from misconfigured LLM call.
**Cons:** Small writing effort; no downside.
**Context:** See Sections 2 (Error/Rescue Map — LLMHallucinationRisk, PHILeakRisk) and Section 3 (Security — prompt injection). This TODO unlocks both gaps.
**Effort:** S (human: 1 day) → CC: 30 minutes
**Priority:** P1 — blocks LLM vendor selection and HIPAA compliance design
**Depends on:** Nothing. Stand-alone PRD edit.

### TODO-002: Define FHIR Record Deduplication Strategy

**What:** Add a deduplication requirements section to the PRD (or architecture doc HK-A) specifying exactly how duplicate FHIR records are handled during multi-provider import and continuous sync.

**Why:** OMOP has no native deduplication mechanism. When the same lab result appears in two provider's FHIR bundles (shared lab, two institutions), or when continuous sync re-imports records already in the system, the current PRD is silent on what happens. Without a defined strategy, engineers will implement divergent or incorrect behavior, leading to duplicate records on the patient timeline and corrupted PatientInfo values (breaking trial matching).

**Required decisions:**
1. Primary dedup key: FHIR `resource.id` within a source system (easy, reliable within one EHR; breaks across systems with different IDs for the same event)
2. Cross-provider dedup: content hash of (patient_id, date, OMOP concept_id, value, unit) — catches the same lab result from two providers
3. Conflict vs. duplicate: define the distinction. Two HbA1c results on the same day with different values = conflict (PHResolution). Two entries for the same HbA1c result = duplicate (deduplicate silently, log).
4. Re-import behavior: on continuous sync, records already in OMOP with matching source_record_id are updated (not re-inserted). Change detection for incremental sync varies by EHR vendor — Epic supports `_since` parameter; others may not. Specify fallback for EHRs without change detection.

**Pros:** Prevents duplicate records on patient timeline. Prevents corrupted PatientInfo flat table. Required for research cohort quality (Section 6 V2).
**Cons:** Non-trivial design decision; requires EHR-specific knowledge of how FHIR resource IDs work across vendors.
**Context:** Discovered during Section 4 (Data Flow) and Section 5 (PRD Quality) review. Blocks ETL design (INF-010–014). Without this, PHRogram cannot be correctly specified.
**Effort:** S (human: 2 days design) → CC: 1 hour
**Priority:** P1 — blocks ETL architecture and PHRogram spec
**Depends on:** Nothing. Should be written before ETL design begins.

### TODO-003: Add NFR-OBS Section (Observability Requirements)

**What:** Add a new NFR section (NFR-OBS-001 through NFR-OBS-008) to the PRD covering operational observability requirements for the V1 platform.

**Why:** The PRD has zero operational observability requirements. PAT-016 and PAT-052 describe patient-visible audit logs (compliance features), but nothing tells the engineering team what to instrument for operations. For a HIPAA system, operational observability is required: you must be able to detect unauthorized PHI access, failing imports, ETL backlogs, and LLM accuracy drift. Without these requirements, silent data quality failures (unmapped FHIR codes, stale PatientInfo, failed ETL jobs) will go undetected for weeks.

**Required requirements:**
- NFR-OBS-001: FHIR import success/failure rate — per provider, per import run. Alert on >5% failure rate.
- NFR-OBS-002: ETL pipeline latency — time from FHIR download to OMOP write. Alert if incremental sync exceeds 10 minutes or full import exceeds 45 minutes.
- NFR-OBS-003: Vocabulary mapping failure rate — count of FHIR codes that couldn't be mapped to OHDSI standard vocabularies per import. Alert on unmapped records so they're surfaced to the data quality team, not silently dropped.
- NFR-OBS-004: PHI access anomaly detection — unusual access patterns (rapid successive queries, access from new IP/device, off-hours bulk access) must trigger alert. Required for HIPAA breach detection.
- NFR-OBS-005: LLM extraction accuracy tracking — sample of extracted fields must be evaluated for accuracy on a weekly basis. Drift detection: if accuracy drops >10% week-over-week, alert.
- NFR-OBS-006: PatientInfo freshness — lag between a data update and PatientInfo regeneration must be monitored. Alert if any patient's PatientInfo is >1 hour stale after a data change.
- NFR-OBS-007: Identity verification failure rate — CLEAR/ID.me success/failure/latency. Alert if downtime exceeds 5 minutes (new patient onboarding blocked).
- NFR-OBS-008: Share link access events — all share link scan/access events logged for patient-visible audit and security monitoring. Alert on access to expired/revoked links (potential replay attack).

**Pros:** Unblocks operational engineering. HIPAA breach detection. Prevents silent data quality failures reaching patients.
**Cons:** Small writing effort; no downside.
**Context:** Discovered in Section 8 (Observability). The gap applies to the entire system — there are no logging or metrics requirements anywhere in the current PRD.

### TODO-015: Add Pre-Computed timeline_event Table for NFR-011 Compliance

**What:** Define and add a pre-computed timeline_event denormalized table to the OMOP schema (alongside PatientInfo), populated by PHRogram during ETL and incremental sync.

**Why:** NFR-011 requires the patient longitudinal timeline to load in under 3 seconds for 10,000 events. The naive approach — a UNION across 5 OMOP domain tables (Condition, Drug Exposure, Measurement, Observation, Procedure) ordered by event_date — takes ~800-1200ms for PostgreSQL alone before API and rendering overhead. At 10,000 events, the UNION + ORDER BY + API layer regularly exceeds 3 seconds on cold queries.

**Required table spec:**

```sql
CREATE TABLE timeline_event (
  event_id         BIGINT PRIMARY KEY,
  person_id        BIGINT NOT NULL REFERENCES person(person_id),
  event_type       VARCHAR(50) NOT NULL,  -- 'condition', 'drug', 'measurement', 'observation', 'procedure'
  event_date       DATE NOT NULL,
  concept_name     VARCHAR(255),          -- OHDSI standard concept name
  value_as_string  TEXT,                  -- human-readable value (lab value + unit, dosage, etc.)
  source_name      VARCHAR(255),          -- provider/institution name
  source_record_id BIGINT,               -- FK to originating OMOP domain record
  has_conflict     BOOLEAN DEFAULT FALSE, -- from conflict_resolution table
  INDEX idx_timeline_patient_date (person_id, event_date DESC)
);
```

- Populated by PHRogram as part of both full import and incremental sync
- Updated on PHResolution decision (update has_conflict flag, re-fetch concept_name from resolved OMOP record)
- Updated alongside PatientInfo in debounced recomputation (TODO-011) — same sync batch trigger
- Timeline API queries ONLY this table (never raw OMOP domain tables for display)

**Performance target:** Single patient, 10,000 rows → index scan → <50ms. Full API round trip (query + serialize + network) → <500ms. Well within NFR-011 3-second target.

**Pros:** Achieves NFR-011. Simple additive table, doesn't change OMOP schema. Same proven pattern as PatientInfo.
**Cons:** Additional table to keep in sync. Mitigated: same debounce mechanism as PatientInfo (one sync job, not per-write).
**Context:** Discovered in Section 4 (Performance Review). Raw OMOP UNION queries will not hit NFR-011 without this pre-computation layer.
**Effort:** S (human: 1 day spec + 2 days implementation) → CC: 1 hour
**Priority:** P1 — NFR-011 compliance. Must be in initial schema design.
**Depends on:** TODO-010 (incremental sync pipeline) — timeline_event must be updated in both full import and incremental sync.

### TODO-014: Define Consent Model — Clinical Sharing vs Research Consent Independence

**What:** Add a formal consent model spec to the PRD clarifying the relationship between clinical sharing permissions (PAT-051) and research consent (PAT-055), with special handling for genomic/biomarker data.

**Why:** The PRD defines clinical sharing permissions (PAT-051: per-category, per-clinician) and research consent (PAT-055: opt-in to share de-identified data with research cohorts) as separate systems, but doesn't define their relationship. Without a formal model, engineers will implement binary research consent (one toggle = all data) which violates GDPR's specificity requirement ('consent must be as specific and granular as the data processing'). Genomic data (BRCA1/2, EGFR, HER2) is re-identifiable even when de-identified — a 2008 NEJM study demonstrated this — and requires a separate explicit consent with re-identification disclosure.

**Required consent model spec:**

1. Clinical sharing permissions (PAT-051) are independent from research consent (PAT-055). Revoking clinical sharing does not revoke research consent, and vice versa.

2. Research consent is per-data-category (matching PAT-051 categories): a patient can consent to research use of labs and vitals but not genomics/biomarkers.

3. Genomics/biomarkers (PAT-026: BRCA1/2, EGFR, KRAS, HER2, ER/PR) require a separate, explicit consent with:
   - Plain-language disclosure of re-identification risk
   - Disclosure of which research partners may access the data
   - Option to consent to aggregate-only access (no individual-level genomic export)
   - This consent is separate from the general research consent toggle

4. Research consent withdrawal triggers immediate removal from active research cohorts (PAT-055) — does not affect clinical sharing.

5. Clinical sharing revocation triggers share link expiry and future-access denial — does not affect research consent.

**GDPR note:** Under GDPR Article 6(1)(a), research consent must be 'freely given, specific, informed, and unambiguous.' Bundling all data categories into one research consent toggle likely fails the 'specific' requirement for genomic data.

**Pros:** GDPR compliance for genomic data. Prevents a consent UI retrofit after first GDPR audit.
**Cons:** More complex consent UI (multiple toggles instead of one). Worth it.
**Context:** Discovered in Section 2 (Spec Quality Review). Connects to NFR-002 (GDPR compliance) and PAT-026 (genomics capture).
**Effort:** S (human: 1 day spec + legal review) → CC: 1 hour spec (legal review is human-only)
**Priority:** P1 — GDPR violation risk. Must be resolved before consent management UI is designed.
**Depends on:** Legal counsel for GDPR genomic consent requirements.

### TODO-013: Add PHResolution Conflict Editability Matrix to PAT-031

**What:** Update PAT-031 to define, per OMOP domain, whether 'create a third, reconciled version' is patient-editable, choose-only (no free text), or requires clinician escalation.

**Why:** PAT-031's 'create a third, reconciled version' option currently allows a patient to enter any value for a conflicting clinical data point. For demographics and patient-reported data, this is correct. For diagnoses, tumor staging, lab values, and genomics, allowing patient-entered clinical values is a patient safety risk: an oncology patient who edits their own tumor stage to qualify for a trial could make a clinically dangerous treatment decision. This is also a liability issue for HealthKey.

**Required PAT-031 addition — conflict editability matrix:**

| OMOP Domain | Editability | Rationale |
|-------------|------------|-----------|
| Person (demographics, contact) | Patient-editable | Patient is authoritative source |
| Observation — patient-reported (symptoms, QoL) | Patient-editable | Patient is authoritative source |
| Condition Occurrence (diagnosis, staging) | Choose-only OR clinician escalation | Staging errors affect trial eligibility; patient safety |
| Measurement (lab values, vitals) | Choose-only (choose most recent or documented source) | Lab values require instrumentation, not patient judgment |
| Drug Exposure (medications) | Partially editable (dates, stopped/continuing status) — not dosage | Patients know their own adherence; not dosage precision |
| Observation — genomics/biomarkers | Clinician escalation only | BRCA1 status is not patient-determinable |
| Genomics (allergy status) | Choose-only OR clinician escalation | Allergy conflicts are safety-critical |

**LLM source quality in PHResolution (from outside voice review):** Add to this matrix: PHResolution conflict display must show source quality alongside each version — provider name, data type (FHIR / manually-uploaded / LLM-extracted), confidence level (verified / low confidence — review carefully). The conflict_resolution table must store source_type and confidence_score from the parsing pipeline (not just source provider name). A patient comparing an Epic FHIR record against an LLM-parsed scanned PDF must see which is which, or they cannot adjudicate the conflict correctly.

**Connects to TODO-007:** The 'clinician escalation' path in this matrix is the same 'defer to clinician' mechanism described in TODO-007 (PHResolution Unresolvable State + Clinical Escalation). These two TODOs should be implemented together.

**Pros:** Prevents patient-entered tumor staging and lab values. Protects HealthKey from liability if incorrect patient-edited data flows into trial eligibility.
**Cons:** Restricts patient autonomy on some domains. The PRD's 'Patient Primacy' principle could be read as permitting free-form editing. But patient primacy means control, not ability to make clinical errors.
**Context:** Discovered in Section 2 (Spec Quality Review). Connects to TODO-007 (clinical escalation path).
**Effort:** S (human: 1 day UX + spec) → CC: 30 minutes
**Priority:** P1 — patient safety. Must be resolved before PHResolution UI is designed.

### TODO-012: Specify Document Parsing Tiers in PAT-012

**What:** Update PAT-012 (Manual Document Upload) to specify four distinct parsing tiers with different tooling, accuracy expectations, and fallback behavior per tier.

**Why:** 'Extract structured data where possible using document parsing' covers four technically distinct problems with wildly different accuracy profiles. A single opaque parser will silently fail on document types it doesn't handle, leaving patients wondering why their scanned oncology reports didn't extract. Oncology patients upload exactly these documents — scanned PDFs from foreign hospitals, printed lab reports, discharge summaries.

**Required PAT-012 additions — four parsing tiers:**

*Tier 1: FHIR JSON / C-CDA XML bundles*
- Deterministic transform (no LLM required)
- Tool: XSLT transform for C-CDA, direct JSON parse for FHIR
- Accuracy: ~100% for well-formed documents
- Fallback: store as attachment if malformed

*Tier 2: Typed PDF / Word documents (machine-generated text)*
- LLM extraction with confidence scoring per NFR-LLM-004
- Tool: PDF text extraction (pdfminer, pypdf) → LLM structured extraction
- Accuracy: ~85-90% for well-formatted clinical PDFs
- Fields below confidence threshold: patient review flag (per NFR-LLM-004)
- Fallback: store as attachment with partial extraction where available

*Tier 3: Scanned paper / handwritten documents*
- OCR + LLM extraction
- Tool: cloud OCR (AWS Textract or equivalent, must have BAA per NFR-LLM-001) → LLM extraction
- Accuracy: ~60-70%; expect high rate of patient review flags
- Inform patient at upload: 'Handwritten documents are extracted with lower accuracy — please review all extracted fields'
- Fallback: store as attachment with best-effort extraction

*Tier 4: DICOM files*
- Metadata-only extraction (study date, modality, body region, institution); image stored as attachment
- Tool: dcm4che or pydicom — deterministic, no LLM
- Image analysis (findings, impressions): explicitly out of scope (V2 per Section 10)
- Patient sees: image thumbnail + metadata card; radiologist report extracted as Tier 2 if PDF accompanies DICOM

**Pros:** Prevents a single opaque parser from silently dropping scanned documents. Sets patient expectations correctly for handwritten note accuracy.
**Cons:** Four parsing paths = more implementation work. But scoping per tier prevents gold-plating (e.g., don't apply LLM to C-CDA XML which needs none).
**Context:** Discovered in Section 2 (Spec Quality Review). Connects to TODO-001 (NFR-LLM) which covers LLM guardrails but doesn't define which tiers require LLM.
**Effort:** S (human: 1 day spec) → CC: 30 minutes
**Priority:** P1 — blocks document upload pipeline design and LLM vendor cost estimation
**Depends on:** TODO-001 (NFR-LLM section) for confidence scoring and BAA requirements on cloud OCR.

### TODO-011: Fix INF-004 PatientInfo Recomputation — Specify Debounced Event-Driven Pattern

**What:** Update INF-004 to replace "re-computed on each data update" with a specified debounced, event-driven recomputation strategy.

**Why:** "On each data update" means one PatientInfo rebuild per OMOP write. An incremental sync for one patient produces 50-200 OMOP writes. At 1,000 daily active patients, that's 50,000-200,000 PatientInfo recomputation events per day hitting PostgreSQL — a performance catastrophe at even early beta scale.

**Required INF-004 additions:**
- PatientInfo recomputation is event-driven: any OMOP write for patient X enqueues a rebuild for patient X
- Recomputation is debounced per sync batch: one 'patient sync completed' event fires per patient per sync, regardless of how many OMOP writes occurred
- PatientInfo and timeline_event (TODO-015) are rebuilt in a single coordinated job chain triggered by 'patient sync completed': PatientInfo first (conflict provisional flags), then timeline_event (reads has_conflict from PatientInfo). This ordering guarantee prevents the patient from seeing a timeline that disagrees with PatientInfo.
- Maximum staleness SLA: PatientInfo must be current within 1 hour of sync completion (aligned with NFR-OBS-006 from TODO-003)
- Recomputation queue: persistent (survives process restart), deduplicated by patient_id (not per-event FIFO)
- Monitoring: PatientInfo rebuild latency and queue depth are operational metrics (feeds NFR-OBS-006)
- On-demand refresh: patients can trigger a manual PatientInfo refresh from the UI (for real-time trial matching before daily sync)

**Pros:** Prevents a naive 'one rebuild per OMOP write' implementation that will hit performance limits immediately at beta. Aligns with standard materialized-view refresh patterns.
**Cons:** Requires a job queue (e.g., Sidekiq, Celery, BullMQ) for debounced rebuild events — small additional infrastructure.
**Context:** Discovered in Section 1 (Architecture Review). INF-004 'populate_patient_info re-computed on each data update' will be implemented naively without this spec.
**Effort:** S (human: 1 day design) → CC: 30 minutes
**Priority:** P1 — blocks PatientInfo implementation; will cause performance failures at beta
**Depends on:** TODO-010 (incremental sync pipeline spec) — debounce fires on sync-batch completion, not per OMOP write.

### TODO-010: Spec Two Distinct ETL Pipeline Architectures

**What:** Add an architecture note (or section to INF-010–014) explicitly separating two pipelines: (1) Full Import Pipeline and (2) Incremental Sync Pipeline.

**Why:** WhiteRabbit, Rabbit-in-a-Hat, and PHRogram are batch ETL design tools built for full-load migrations. They cannot perform incremental change detection or OMOP upsert semantics. PAT-015 (Continuous Sync, Must Have) requires daily re-pull from connected providers — a fundamentally different pipeline. Without explicit separation, engineers will either build PHRogram to do both (it can't), or build a single pipeline and break one mode.

**Required spec additions:**

*Full Import Pipeline (batch):*
- PHRofile → WhiteRabbit → Rabbit-in-a-Hat → PHRogram → bulk OMOP insert
- Triggered: on initial provider connection or patient-requested full re-import
- Auth: SMART Backend Services (Bulk FHIR)
- Target: NFR-012 (30 min for 5-year history)

*Incremental Sync Pipeline (streaming/scheduled):*
- FHIR _lastUpdated polling per provider per patient (or EHR webhook where supported)
- Extract only new/changed FHIR resources since last sync timestamp
- Incremental OMOP transformation (shared logic with PHRogram scripts, but upsert semantics)
- Upsert into PostgreSQL (ON CONFLICT DO UPDATE) — not full reload
- PHResolution conflict detection triggered on changed records only
- PatientInfo recomputation for affected patients only
- Auth: SMART on FHIR standalone (patient-scoped, per-provider credential)
- Target: NFR-012 (5 min for incremental sync)
- Fallback: EHRs without _lastUpdated support → full re-pull with dedup, not incremental

**Pros:** Prevents engineers from building PHRogram for both modes (it can't do both). Prevents duplicate records from re-inserting already-synced data.
**Cons:** Two pipelines = two codepaths to maintain. Shared transformation logic must be extracted as a library used by both.
**Context:** Discovered in Section 1 (Architecture Review). The PRD currently treats ETL as a single system (INF-010–014), conflating batch and incremental.
**Effort:** S (human: 2 days design doc) → CC: 1 hour
**Priority:** P1 — blocks ETL implementation design
**Depends on:** TODO-009 (SMART on FHIR) — incremental pipeline uses patient-scoped auth.

**What:** Add three performance SLAs to Section 9.2 (NFR-Performance) that are currently missing.

**Why:** Missing SLAs mean engineers won't know when they've failed. Without a target, export generation will be slow, conflict detection latency undefined, and consent propagation undefined.

**Required NFR additions:**

### TODO-006: GDPR Right-to-Erasure Architecture for OMOP

**What:** Design and specify a patient data erasure architecture that works with OMOP CDM's structure before any table schemas are finalized.

**Why:** OMOP has no native soft-delete. A patient invoking GDPR right-to-erasure (NFR-002) requires cascading deletes across every OMOP domain table keyed to person_id (Person, Observation Period, Condition Occurrence, Drug Exposure, Measurement, Observation, Procedure Occurrence, Device Exposure, Death, Note), the PatientInfo flat table, PHResolution logs, import audit logs, share link history, and raw FHIR bundle storage. If not designed before the first OMOP write, this becomes a multi-day engineering emergency at first erasure request. Any OMOP exports generated before erasure create orphaned de-identified records that may require a separate retention/deletion policy.

**Required decisions:**
1. Soft-delete approach: tombstone person_id in a deletion log + background cascade, or synchronous cascade on erasure request?
2. person_id pseudonymization: use a pseudonymized person_id in all OMOP tables (not the real patient identifier) so deletion of the mapping record effectively anonymizes without cascade?
3. Raw FHIR bundle storage: retention policy after erasure — delete immediately or retain for 30 days (legal hold period)?
4. OMOP exports: if a researcher export was generated before erasure, what obligation exists? (GDPR de-identification exemption may apply for research exports)
5. Audit log retention: HIPAA requires 6-year audit log retention; GDPR requires deletion. Conflict requires legal advice and a reconciliation policy.

**Pros:** Prevents a compliance emergency at first erasure request. Informs table schema design from day one.
**Cons:** Non-trivial legal + engineering intersection. Requires a GDPR/HIPAA legal opinion on the audit log conflict.
**Context:** Surfaced by outside voice reviewer. Directly conflicts with HIPAA audit log retention (6 years) vs GDPR right-to-erasure. This intersection needs legal review before architecture decisions are finalized.
**Effort:** M (human: 1 week design + legal review) → CC: L (2 hours architecture, but legal review is human-only)
**Priority:** P1 — must be resolved before first OMOP table schema is created
**Depends on:** Legal counsel. Architecture doc (HK-A) must incorporate the decision.

### TODO-007: Add PHResolution Unresolvable State + Clinical Escalation Path

**What:** Add requirements for cases where a conflict cannot be resolved by the patient alone — specifically clinical conflicts (tumor staging, treatment history, allergy status) that require clinical judgment. Also specify the patient-visible state during the resolution window.

**Why:** The full PHResolution workflow (PAT-031) currently assumes patients can resolve all conflicts. But oncology conflicts like T2N1M0 vs T3N0M0 staging discrepancy or contradictory BRCA1 status require a clinician to adjudicate. Without an "unresolvable" state and a clinical escalation path, these conflicts will either be left permanently unresolved (PatientInfo stays provisional forever) or the patient will make a clinically dangerous decision. This is a patient safety issue.

**Required additions to PAT-031:**
- "Defer to clinician" option for each conflict (alongside "Use source A" / "Use source B")
- "Unresolvable — pending clinical review" state for PatientInfo (extends provisional flag)
- Mechanism to flag a conflict for the patient's next appointment (adds to Appointment Preparation View)
- Runbook for what happens if a patient permanently defers a conflict — does PatientInfo stay provisional indefinitely?
- **PHResolution PENDING STATE UX (added from outside voice review):** Specify what the patient sees WHILE a conflict is pending resolution (before they've made a decision). Options: (a) most-recent source wins, shown with 'conflict pending' badge (aligns with CEO review decision), (b) data hidden until resolved (bad UX — hides important records), (c) both versions shown with uncertainty flag. Option (a) is preferred — data is available, clearly flagged. The pending state must be distinct from the post-escalation state. Pending = 'waiting for patient'; Escalated = 'waiting for clinician.'

**Pros:** Prevents dangerous patient self-adjudication on clinical judgment calls. Required for a product used by cancer patients making trial eligibility decisions.
**Cons:** Adds complexity to the PHResolution workflow. The "defer to clinician" path requires the Appointment Prep view (PAT-043) to exist or a simpler flagging mechanism.
**Context:** Surfaced by outside voice reviewer. The main review accepted PHResolution as a UX problem; the outside voice correctly identifies it as a clinical judgment problem for certain conflict types.
**Effort:** S (human: 2 days UX + 1 day engineering) → CC: 30 minutes
**Priority:** P1 — patient safety. Required before PHResolution ships.
**Depends on:** PHResolution (PAT-031) must be updated. Clinician sharing flow (PAT-050) provides the escalation path.

### TODO-008: Add Raw FHIR Bundle Storage Requirement to INF Section

### TODO-017: Refresh `loinc_common.json` on LOINC release

**Context:** Discovered in `/plan-eng-review` delta review of the lab upload design doc (docs/patient-app-lab-upload-design.md §3.4). Added because "we'll remember to run it" decays to "nobody ran it for 3 years" without a reminder captured somewhere.
